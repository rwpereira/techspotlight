🤖 feature #12566 OpenSpec Spec-Driven Agrotrace openspec.config.ts
OpenSpec no Projeto Agrotrace
❌ problema
O Agrotrace cresceu e virou base de vários projetos terceiros (PEC, Agroplus, 3S…). Mudanças de feature começavam direto no código, sem uma especificação compartilhada e versionada — gerando ambiguidade entre o que foi pedido e o que foi entregue, retrabalho e dificuldade de alinhar mudanças entre API/Web e Mobile.
✓ solução
→ Configuração do framework OpenSpec no Agrotrace para adotar um fluxo Spec-Driven.
→ Especificações passam a viver versionadas no repositório, num ciclo proposta → spec → implementação.
→ Padroniza como mudanças são descritas e revisadas antes de virar código.
📈 resultado
Base estabelecida para guiar features pela especificação antes da implementação. Melhor alinhamento entre time e stakeholders, menos divergência de escopo e fundação para escalar o desenvolvimento conforme o Agrotrace ganha derivados.
// ciclo spec-driven
📝 Proposta — change descrita em markdown
↓
📐 Spec — revisada e versionada no repo
↓
⚙️ Implementação — guiada pela spec
↓
✅ Archive — spec vira fonte da verdade
base de PEC · Agroplus · 3S · derivados do Agrotrace
// spotlight 2 — Carlos — 10 min ⏱
⚡ feature #12561 contexto #12545 CheckWork ollama-ocr.service.ts
Modelo LLM local para dar suporte ao OCR de NFs
❌ problema
A extração de dados de Notas Fiscais no CheckWork dependia de OCR via contas/serviços externos de IA — sujeito a custo, rate-limits e dependência de terceiros, exigindo até contas de fallback. Buscou-se uma solução de OCR baseada em IA rodando on-premise.
✓ solução
→ POC inicial com GLM-OCR (~1s por imagem) e benchmark entre modelos → escolha do gemma3:4b.
→ Serviço self-hosted via Ollama, com API própria abstraindo a chamada e fazendo o parse da resposta no formato do input.
→ Rate-limit + fila para suportar volumes maiores de requisições.
→ Integração no app, validação no ambiente DEV e notificações via OneSignal.
📈 resultado
LLM self-hosted resolvendo NFs em ~1s/imagem, reduzindo a dependência de contas externas de IA. Serviço exposto e validado, com benchmark, em uso no CheckWork.

// API própria abstrai o Ollama (gemma3:4b)
async extrairNF(img: Buffer) {
  const res = await this.queue.add(() =>
    ollama.generate({
      model: "gemma3:4b",
      images: [img.toString("base64")],
      prompt: NF_PROMPT,
      format: "json"
    })
  )
// parse no formato do input
  return this.parseToInput(res.response)
}

// spotlight 3 — Elias — 10 min ⏱
📊 feature #12624 Form Dinâmico Sincronização blocos-repetiveis.service.ts
Respostas Repetíveis — blocos no Form Dinâmico
❌ problema
O formulário dinâmico não permitia repetir blocos de perguntas — quando o mesmo conjunto precisava ser respondido N vezes (vários itens/registros), não havia suporte nativo, forçando duplicação manual ou estruturas rígidas.
✓ solução
→ Levantamento de requisitos e regras de negócio do recurso.
→ Novas entidades + migrações para as tabelas dos blocos.
→ Novas rotas no módulo de sincronização de dados.
→ Componente para exibir as perguntas do bloco e CRUD completo (salvar, editar, excluir) das respostas com regras de negócio.
→ Sincronização bidirecional (baixar e enviar) dos dados dos blocos.
📈 resultado
Suporte completo a blocos/respostas repetíveis no formulário dinâmico. CRUD e sync finalizados e testados (baixar e enviar).

app.post("/ocr/nf", async (req, res) => {
  const out = await extrairNF(req.file.buffer)

Pontos bons para comentar
1. Sem dependência externa: saímos de contas/serviços de IA de terceiros para um serviço próprio.
2. Parse no formato do input: resposta da LLM já volta no shape esperado pelo CheckWork.
3. Escala controlada: fila + rate-limit deixam o serviço previsível sob volume.
4. Custo: modelo pequeno (4b) roda local e cobre o caso de OCR de NFs.
